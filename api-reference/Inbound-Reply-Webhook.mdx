## Inbound Reply Webhook

When a consumer replies to a text you sent through the [Texting endpoints](/api-reference/Texting-Overview), we deliver that reply to an HTTPS endpoint you own. Every reply is delivered — we do not filter or auto-answer them on your behalf. You only receive your own organization's replies.

Send us your endpoint URL and we will configure it, along with a signing secret.

<Note>
  If no endpoint is configured, replies are still recorded — read them at any time with [List Text Messages](/api-reference/endpoint/Text-Messages).
</Note>

## Webhook Notification

```
X-CollectWise-Event: text.inbound
X-CollectWise-Timestamp: 1755432000
X-CollectWise-Message-Id: 4d1a0b7c-9e2f-4c31-8a77-2b6f0d1e5c44
X-CollectWise-Signature: sha256=<hex hmac>
```

```json
{
  "event": "text.inbound",
  "orgId": "05e617d3-2b96-45c4-be30-3ad2d9d3f842",
  "messageId": "4d1a0b7c-9e2f-4c31-8a77-2b6f0d1e5c44",
  "inReplyTo": "1b1f0a9e-6f4e-4f4b-9a2e-1f2d3c4b5a69",
  "accountId": "50041",
  "conversationId": "conv_087b83bb525d4fceaaa01a4234b6b012",
  "debtorId": "your-reference-number",
  "from": "+13313048434",
  "to": "55555",
  "message": "when is my payment due",
  "messageType": "sms",
  "mediaUrls": null,
  "receivedAt": "2026-08-17T12:00:00.000Z"
}
```

| Field | Description |
| --- | --- |
| `messageId` | Id of this reply. Use it as your de-duplication key — delivery is at-least-once. |
| `inReplyTo` | The `messageId` of the send this reply answers. `null` when it cannot be attributed to one of your sends — a consumer texting in cold, or a conversation idle more than 7 days. |
| `debtorId` | The reference you sent on that message, or `"UNKNOWN"` if the number has no send on record. |
| `conversationId` | Thread id. Messages to and from a number group into one conversation. |
| `from` | The consumer's number, in E.164 format. |
| `to` | The number or short code they replied to. |
| `messageType` | `sms` or `mms`. `mediaUrls` is non-null only for MMS. |

## Verifying the signature

Each delivery is signed as `sha256=HMAC_SHA256(secret, "{timestamp}.{raw body}")`, using the secret as raw UTF-8 bytes and lower-case hex for the digest. Compute it over the **raw request body before JSON parsing** — re-serializing the parsed body changes the bytes and the signature will not match.

```javascript
const expected =
  "sha256=" +
  crypto
    .createHmac("sha256", secret)
    .update(`${headers["x-collectwise-timestamp"]}.${rawBody}`)
    .digest("hex");
```

Check your implementation against this vector — secret `whsec`, timestamp `1755432000`, body `{"a":1}`:

```
sha256=0fe730fb2fb798f23d9b724ebb086d14d50ff27a15eb4bbb6f5cf70b334e4b59
```

Without a configured secret we deliver unsigned and omit the header.

## Responding

Respond `2xx`. A non-2xx or a network error is retried up to 3 times with a short backoff, reusing the original timestamp and signature; a `4xx` is treated as permanent and not retried. If your endpoint is down for a period, use [List Text Messages](/api-reference/endpoint/Text-Messages) with `since` to backfill what you missed.
